# The PATA Framework

**PATA** is a four-layer model for structuring every entity in an application: **P**arameters → **A**ssets → **T**ransactions → **A**nalytics. It's a way of asking, for any new table, field, or piece of business logic: *which of these four buckets does this belong to?* — before writing a line of schema or UI code.

The core rule that makes it work:

> **Nothing in the app should be hard-coded.** Anything that configures behavior, filtering, categorization, or display belongs in Parameters, not in application code.

## The four layers

### P — Parameters
Settings and configuration: categories, sub-categories, country codes, city codes, user types, statuses, formats, roles — anything that defines *the shape of the choices* the app offers. Parameters are admin-managed via CRUD, not baked into the codebase.

*Examples: a list of session modalities (yoga, breathwork, meditation…), delivery formats (online / in-person / hybrid), user roles, booking statuses, currencies.*

### A — Assets
The core domain entities — the actual "things" the system manages. Users, listings, products, rooms, facilitator profiles. Assets typically *reference* Parameters rather than embedding raw values (e.g., an offering references a `modality` from the Parameters table instead of storing the string `"yoga"` directly).

### T — Transactions
Records generated by users interacting with Assets: bookings, orders, purchases, reservations, messages, reviews. Transactions are where the app's actual activity and history live, and their state fields (e.g., `pending` / `confirmed` / `cancelled`) are themselves Parameters, not hard-coded strings.

### A — Analytics
Insights and dashboards derived from the other three layers: revenue by category, booking trends, engagement metrics, supply/demand views. Analytics is usually the last layer to get built, but designing Parameters and Assets cleanly from day one is what makes Analytics possible later without a rewrite.

## Why this is a good approach

**1. Nothing requires a deploy to change.**
If "session type" is a Parameters table instead of a hard-coded enum or a free-text field, an admin can add "Reiki" or "Sound Bath" as a new category from a settings screen. If it were hard-coded, that's a code change, a PR, a review, and a deploy for what is fundamentally a content decision, not an engineering decision.

**2. It forces a real separation between configuration and logic.**
Engineers keep asking "is this a business rule, or is this just data the business wants to control?" That question alone prevents a huge amount of accidental coupling — UI dropdowns, filter logic, and validation all end up reading from the same source of truth instead of three different hard-coded lists that drift out of sync.

**3. It kills an entire class of bugs.**
Free-text fields masquerading as categories (`modality: text`) inevitably diverge — "Yoga", "yoga", "YOGA " all exist in production, filtering silently misses records, and nobody notices until a customer complains. A Parameters table with a `slug` + FK relationship makes that class of bug structurally impossible.

**4. It scales naturally to multi-tenant / white-label.**
Because everything configurable lives in Parameters rather than code, spinning up a differently-branded or differently-configured instance of the same app becomes a data problem, not a fork.

**5. It gives non-engineers real control.**
Founders, ops people, and admins can shape the product — add a category, rename a status label, adjust what shows in a dropdown — without touching code or waiting on engineering. This is often the difference between an admin panel that's genuinely useful and one that's decorative.

**6. It makes the codebase self-documenting.**
Once every table is classified as P, A, T, or A, a new engineer (or an AI assistant) can look at the schema and immediately understand the shape of the domain: "these are the choices, these are the things, these are the events, this is the reporting." That's a much faster mental model to build than reverse-engineering intent from a pile of unstructured tables.

## What "compliant" looks like

A well-formed Parameters table follows a consistent pattern:

```sql
CREATE TABLE "modalities" (
  "id"          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "slug"        varchar(80) NOT NULL UNIQUE,
  "label"       text NOT NULL,
  "description" text,
  "sort_order"  integer NOT NULL DEFAULT 0,
  "active"      boolean NOT NULL DEFAULT true,
  "created_at"  timestamp DEFAULT now() NOT NULL,
  "updated_at"  timestamp DEFAULT now() NOT NULL
);
```

- Admin CRUD routes: `GET/POST /api/admin/parameters/modalities`, `PATCH/DELETE /api/admin/parameters/modalities/:id`
- Referenced by FK from Asset/Transaction tables (by `slug` or `uuid`) — never duplicated as a raw string
- Seeded with sensible defaults so the app works out of the box
- Never hard-coded as an enum, a `switch` statement, or a magic string anywhere in application code

## Applying it to a new feature

Before writing schema or UI for something new, ask in order:

1. **Is this a choice the business wants to control without a deploy?** → Parameters.
2. **Is this a "thing" the system manages?** → Asset.
3. **Is this a record of something happening?** → Transaction.
4. **Is this a derived insight from the above?** → Analytics.

If a field feels like it should be free text or a hard-coded list of options, that's usually a signal it's actually a Parameter in disguise.
